At `bf6cc0b` (2026-11-01, "D5 Freight Delivery v2 Offline Implementation Complete") all five payload files plus `accepted-digests.json` and `verification.json` were rewritten in one commit — and the comparison shows the rewrites are **pure re-serialization**: parsing the old and new blobs as JSON gives *content-identical* values for `supplemental.json`, `correspondence.json`, `manifest.json`, and `verification.json` (verified programmatically; `recipe.json` likewise, same fields/values, one-line compact → tab-indented). 3. **The pipeline itself is healthy at the current code state — a /tmp probe repaired the seal in a copy and walked the full chain.** With `accepted-digests.json` set to the on-disk digests in a `/tmp/opencode/e207_p08_probe/fixture` copy (repo untouched), `admit()` succeeds, `optimize_candidate_network` (P05/CP-SAT, offline) succeeds, `semantic_checks` pass, and the derived `evidence` record is **content-identical** to the frozen `verification.json` (byte-comparison still fails, because `verification.json` was also re-serialized to tab-pretty form while the test compares `json_bytes(record)` — compact canonical — byte-equal to it at `tests/test_p08_controlled_e2e.py:542`). ## §2 Budget-signature ×3 — mechanism: the intentional 512→2048 tile-classification widening left three 512-era seals in place (proven, commit-dated; extras' verdict ANSWERED)

**E207 record (capture lines 2133, 2188, 2189 + assertion bodies):**

- `tests/test_classification_execution.py::test_sealed_budgets` — `assert 410 == 103` on `pages_limit` (`tests/test_classification_execution.py:121`).
- `tests/test_terrain_classification_preparation.py::test_prepare_materializes_a_pending_authorization_candidate` — sealed `stored["budgets"]` dict expects `pages_limit: 103`, `total_response_bytes_limit: 103 * 508` (`tests/test_terrain_classification_preparation.py:58-60`); the prepared candidate now carries 410 / 208,280.
- `tests/test_world_correspondence.py::test_fallback_schedule_is_sealed_and_explicit` — `assert 208280 == (103 * 508)` on `facts_response_bytes_limit` (`tests/test_world_correspondence.py:53`).

**Mechanism (one shared cause, three seal sites):**

- The computed values come from two constants: `CLASSIFICATION_PAGE_LIMIT = (CLASSIFICATION_MAX_REGION_TILES + PAGE_SIZE - 1) // PAGE_SIZE` and `CLASSIFICATION_TOTAL_RESPONSE_BYTES_LIMIT = CLASSIFICATION_PAGE_LIMIT * MAX_RESPONSE_BYTES` (`app/simulation/openttd/tile_classification.py:640-641`), with `PAGE_SIZE = 5` and `MAX_RESPONSE_BYTES = 508` (`app/simulation/openttd/tile_facts.py:16,18`). Consumed by all three tests' subjects: `app/simulation/openttd/proof/classification_execution.py:382`, `app/simulation/openttd/proof/terrain_classification_preparation.py:360-361`, `app/simulation/openttd/proof/world_correspondence.py:177`.
- The constant was born at 512 tiles (`d4a0550`, 2026-10-18 — `CLASSIFICATION_MAX_REGION_TILES = 512` in that commit's blob) → ceil(512/5) = **103** pages, 103 × 508 = **52,324** bytes — exactly what the three tests seal, i.e. green at birth.
- `5e398db` (2026-11-07, "widen the random-world capture seal to 2048 tiles (ramrom production round)") moved it to 2048 → ceil(2048/5) = **410** pages, 410 × 508 = **208,280** bytes. The module comment documents this as intentional product scope, not drift: "the ceiling is the shared census plan cap, explicitly widened for the ramrom production 2048-tile profile (docs/specs/ramrom-product.md §2). Retained records stay valid; nothing is silently reinterpreted." (`tile_classification.py:635-639`.) The widening commit updated `tests/test_tile_classification_receipt.py` (+4/−4) but **not** the three budget-seal tests.
- The widening does not invalidate any retained observation: the sealed plans still run 90 pages over the 450-tile seed-17 region (`tests/test_terrain_classification_preparation.py:55-57` — `pages_count == 90`), and 90 ≤ 103 ≤ 410 — only the *limit* constants moved. The three tests are the only places still pinning the retired 512-era ceiling.

**Extras' new-vs-pre-existing verdict — ANSWERED (evidence-backed):** pre-existing in the tree **since `5e398db`, 2026-11-07** — red continuously from that commit to E207's head (no later commit touches the constants or these three tests; verified by `git log -S`/per-file logs). It is "new" only relative to the sealed legacy-53 set, which was frozen hours *earlier the same day* (`bf5262c` precedes `5e398db` in `git log --reverse` order, both dated 2026-11-07) — which is exactly why these three are absent from the sealed 53 and surfaced at the first full-suite run. Not an E207-run artifact, not flake, not order-dependent: the arithmetic is deterministic.

**Recommended disposition input for ticket 07 — REPAIR (test seals), not a code bug:** update the three seals to the widened constants (410 pages / 208,280 bytes), or better, derive them from the module constants rather than literals so a future widening cannot silently desynchronize again. The widened ceiling is the documented intended state; sealing these three as "won't fix" would freeze a stale contradiction into the exit gate. No `artifacts/` implication — nothing retained is reinterpreted by either state of the constant.

## §3 Workspace-retention ×1 — mechanism: system-load flake in the kernel-endpoint closure gate skips the sole workspace-disposal call (proven by on-demand reproduction; extras' verdict answered in part)

**E207 record (capture lines 1986-2045):** `tests/test_qualification_preparation.py::test_finalization_failure_cannot_publish_qualification[terminal]` fails at `tests/test_qualification_preparation.py:386` — `assert not p.spec.workspace.root.exists()` — with the runtime workspace `prelaunch/isolated/openttd-15.3-nct_7cgp` still existing after the run ended MOCK_FAILED/FAILED. The `[integrity]` sibling passed.

**Mechanism (static chain, every link with file:line):**

1. The only workspace-disposal site in the qualification attempt flow is `finalize_cleanup(prepared, frozen, cleanup)` at `app/simulation/openttd/proof/raw_production_attempt.py:428`, which delegates to `dispose_and_verify` → `prepared.dispose()` (`app/simulation/openttd/proof/ownership.py:159`, gated by `finalize_cleanup` at `:193-201`).
2. That call is gated by `if not cleanup.get("sockets_closed"): raise ValueError("Closed endpoints not proved")` (`raw_production_attempt.py:426-427`). `cleanup["sockets_closed"]` is assigned from `verify_cleanup_endpoints(...)` at `:397-401`; if that function **raises**, the assignment never happens and the exception is absorbed by the catch at `:405`.
3. `verify_cleanup_endpoints` (`app/simulation/openttd/proof/endpoints.py:167-217`) scans the live kernel socket tables (`kernel_socket_rows()`, `/proc/net/tcp{,6}`) and `_residual_socket` (`:93-139`) raises `ValueError("Live or ambiguous endpoint socket: …")` (`:134`) for **any** row whose local *or remote* port equals one of the attempt's two frozen ports, from **any process on the machine**, in any state other than TCP TIME_WAIT (kernel state 6).
4. The attempt's two ports are **random ephemeral picks frozen at prepare time** — `prepare_proof` calls `EndpointReservation.allocate()` with defaults, i.e. `bind(("127.0.0.1", 0))` (`app/simulation/openttd/proof/harness.py:265`, `:114-130`) — so every run scans two arbitrary ports from the ephemeral range.
5. Therefore: if any unrelated process on the system happens to hold a live socket (LISTEN/ESTABLISHED/SYN_RECV, TCP or UDP) on either of those two arbitrary ports at the scan instant, the closure gate raises → `finalize_cleanup` is skipped → the workspace is retained → with the test's `[terminal]` failure injection (`qualification_lineage.retain_attempt_identity` monkeypatched to raise, `tests/test_qualification_preparation.py:357-362`) firing later inside `terminal()` (`raw_production_attempt.py:516`, caught at `:521-528`), the run still ends MOCK_FAILED / states[-1] "FAILED" / observation incomplete — every earlier assertion holds and only the workspace assertion (`:386`) fails. That is the exact E207 symptom. (The `[terminal]` injection is **not** the cause of the retention; it only sets the failure shape the test then checks. The retention is caused by step 3.)

**Evidence beyond the static chain:**

- **Focused runs all pass on the current tree** (each a fresh diagnostic run): `[terminal]`+`[integrity]` alone; the whole `tests/test_qualification_preparation.py` (60 passed); the eight suite files that touch the same machinery + the target (336 passed, 1 skipped); and the 39-file alphabetical neighbor block from `tests/test_p08_controlled_e2e.py` up to the target file + the target (which reproduced exactly the 51 P08 reds and nothing else). The deterministic in-code path always disposes the workspace before the terminal-failure catch.
- **On-demand reproduction with the real production scan** (`/tmp/opencode/e207_endpoint_probe.py`): the driver replicates the `[terminal]` test and, standing in for an unrelated suite/process, holds one live LISTEN socket on the attempt's frozen game port from the instant the endpoint reservation releases it. Every element of the E207 failure is reproduced (same assertion outcome, same state shape, workspace retained) with the production kernel scan doing the refusing.

**Extras' new-vs-pre-existing verdict — answered in part, honestly split:**

- *Not a post-freeze code regression*: every module on this red's path (`endpoints.py` last change `16345fa` 2026-10-14; `raw_production_attempt.py` / `qualification_lineage.py` `6a0da37` 2026-10-08; `ownership.py` `ce28899` 2026-10-22) predates the legacy-53 freeze (`bf5262c`, 2026-11-07), and the test file's last change (`524ce13`, 2026-11-08, the E153 stderr-windowing round) is outside this test's disposal/gate path. The red at E207 is a single observed instance of a proven flake class, recorded at its own identity; it must not be relabeled as a code defect, and the exact colliding process/port of the E207 run is not recoverable from the capture (recorded as a preserved UNKNOWN, §8).
